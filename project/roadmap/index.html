    Roadmap & status¶

    This page is the single source of truth for "is X actually built yet?" — updated the same day any item's status changes, not retroactively. If a page elsewhere in this guide seems to claim more than this page shows as done, trust this page.

    Last updated: 2026-10-26

    Phase 0 — scaffold¶

    • [x] Git repository, .gitignore
    • [x] pyproject.toml — packaging, dev/docs extras
    • [x] Python virtual environment, editable install verified
    • [x] LICENSE (Apache-2.0) + NOTICE
    • [x] This documentation site (MkDocs + Material)

    Rename note: the project was originally named graphcheck. Renamed to graphtrace on 2026-10-18 — graphcheck collides on PyPI with an unrelated, actively-published Neo4j graph-data-quality tool of the same name, confirmed before anything of this project went public. Package, imports, CLI flag names (--gt-mode, --gt-report, --gt-export), env var (GRAPHTRACE_MODE), config filename (graphtrace.yaml), the internal plan doc, and the top-level folder were all updated together in one pass, not left half-renamed.

    Week 1 — foundations¶

    Goal (per the build plan): plugin entry point, Trajectory, recorder, run_graph, core assertions, demo agent — 10 tests on a demo agent passing in live mode.

    Status: met (2026-10-22). Both halves are done and verified: the framework-agnostic data model/assertion API, and the LangGraph-specific recorder/runner/interceptors/plugin/demo agent.

    • [x] core/trajectory.py — LLMCall, ToolCall, Step, Trajectory dataclasses plus derived properties (path, visits, tool_calls, llm_calls, final_message, cost_usd, latency_s, tokens_total). Deliberate fix versus the original architecture plan: cost_usd is a field precomputed per LLMCall, not something Trajectory computes by reaching into a pricing table — the original plan would have made core depend on the LangGraph-specific layer, breaking the project's own layering rule. 7 tests, see Core concepts.
    • [x] core/errors.py — TrajectoryAssertionError (subclasses AssertionError so pytest.raises(AssertionError) still catches it) plus an index-by-index path diff formatter, so a path mismatch reads as a diff, not two dumped lists.
    • [x] core/matchers.py — any_str(), the one matcher the architecture plan actually names; a Matcher base class ready for more the day a real test needs one.
    • [x] core/assertions.py — all 12 assert_* functions. Two deliberate scope decisions versus the original plan, both documented on Assertions: assert_path's ... gap supports exactly one gap (a second raises ValueError rather than guessing which gap a mismatch belongs to), and assert_retries specifically means "a node re-entered after one of its own tool calls errored," not just "visited more than once" — distinct from assert_visits. The 12th, assert_tool_calls_match, is adopted deliberately from langchain-ai/agentevals' own trajectory-match evaluator (strict/unordered/subset/superset modes) rather than invented. 30 tests.
    • [x] frameworks/base.py — the FrameworkRunner Protocol, built before the LangGraph implementation below. Added to the plan on 2026-10-21 specifically so v0.4's CrewAI/AutoGen support (see Multi-framework support) is a new package later, not a refactor of a shipped one. src/graphtrace/py.typed added alongside it (PEP 561 marker, so the Protocol type-checks for an external implementer) — proactively, since this project has no mypy wired up yet to actually confirm the Protocol is satisfied correctly; see Contributing.
    • [x] frameworks/pricing.py — token → USD table, sets LLMCall.cost_usd at record time.
    • [x] frameworks/langgraph/interceptors.py — patches BaseChatModel.invoke/ainvoke and BaseTool.invoke/ainvoke. Corrected from the original plan's _generate/_run: every concrete chat model (OpenAI's, Anthropic's, LangChain's own GenericFakeChatModel) overrides _generate itself, so patching the base class's version intercepts nothing real — confirmed by hand before trusting it. Attribution uses config["metadata"]["langgraph_checkpoint_ns"] (a "{node}:{task_id}" string LangGraph itself attaches), not the originally-planned contextvars — a ContextVar set while consuming the event stream doesn't survive into the ThreadPoolExecutor worker thread LangGraph actually runs parallel nodes on, confirmed with a threading.current_thread() probe before relying on it.
    • [x] frameworks/langgraph/recorder.py — turns LangGraph's debug stream into Steps (subscribing to debug alone; updates turned out to duplicate task_result.result exactly). Added a flush() step and resume-dedup logic beyond the original design: a step paused on an interrupt never gets a settling checkpoint event, and resuming re-runs it under the same task id, which would otherwise show up as a duplicate.
    • [x] frameworks/langgraph/runner.py — run_graph() and arun_graph().
    • [x] plugin.py — pytest entry point (pytest11), run_graph fixture. Scope reduced from the original plan: --gt-mode and the cassette/judge fixtures aren't added yet since they'd do nothing today.
    • [x] examples/refund_agent/ — a demo agent to record and assert against for real. Writing its tests caught a real bug in the agent itself: refund unconditionally refunded regardless of whether the human approved, a missing conditional edge.

    Week 2 — record, replay, cassettes, config¶

    Goal (per the build plan): 20+ tests pass offline (no real LLM/tool calls) in under 30 seconds.

    Status: met (2026-10-22).

    • [x] replay/cassette.py — YAML cassettes via ruamel.yaml round-trip mode, proven byte-identical on a load-then-save round trip. Real bug found along the way: round-trip mode wraps a loaded float in a ScalarFloat subclass (to preserve exact formatting), which then broke a replayed tool result the moment it flowed into LangGraph's own state and got msgpack-serialized by its checkpointer. Fixed with to_plain_python(), applied only when a value is about to flow back into real code, never on a value still destined for the cassette file.
    • [x] replay/matcher.py — node/kind/hash(request)/occurrence keys; two identical requests from the same node (a retry) match their own two recorded entries in order.
    • [x] replay/modes.py, replay/context.py, replay/engine.py — resolve_call(), the generic record/replay decision tree, kept framework-agnostic (plain YAML-safe data in and out) so a future CrewAI/AutoGen interceptor (v0.4) reuses it unmodified.
    • [x] frameworks/langgraph/interceptors.py/runner.py made mode-aware. Verified by recording the Week 1 demo agent once, then replaying it with the real underlying BaseChatModel.invoke/BaseTool.invoke patched to raise if ever actually reached — zero real calls, proven by direct observation, not inferred from the replay logic's own correctness.
    • [x] core/normalize.py (the built-in timestamp/UUID rules), core/budgets.py (the config-driven default-budget check).
    • [x] config.py — graphtrace.yaml loading, pydantic, strict. framework: crewai (not valid until v0.4) is rejected at load time, not just documented as unsupported.
    • [x] plugin.py extended: --gt-mode CLI flag, cassette directory from config, and the run_graph fixture now auto-applies budgets.default after every call — a test that never calls assert_budget(...) itself still fails if the configured default is exceeded.

    103 tests pass today (pytest from a clean pip install -e ".[dev]") — full regression, every file, in about 2 seconds. See Installation to verify this yourself.

    Week 3 — judge, trace-to-test, report, CLI¶

    Goal (per the build plan): the judge contract and calibration, trace importers (Langfuse/OTel/LangSmith), codegen/test_writer.py, the HTML report, and a real graphtrace CLI — flipping every "Planned" guide page above from aspiration to real, verified behaviour.

    Status: met (2026-10-26).

    • [x] judge/rubric.py, judge/client.py — strict pydantic Rubric/Criterion, JudgeClient (litellm imported lazily, inside ask_json() alone — constructing a client or hitting a cassette-replayed verdict never needs it installed), grade() reusing replay/engine.resolve_call() directly so a judge verdict is cached exactly like an LLM/tool call.
    • [x] judge/calibrate.py — per-criterion agreement and Cohen's kappa against a human-labelled calibration set. Real correction found by checking the math by hand: this project's own build plan originally claimed "full disagreement scores kappa 0.0" — false for balanced labels; a perfect inversion actually scores -1.0 (real anti-correlation, worse than chance), confirmed against both the hand-derived formula and the real installed sklearn. See Judge & calibration for the corrected explanation.
    • [x] importers/base.py, importers/{langfuse,otel,langsmith}.py — one shared NormalizedTrace/NormalizedSpan shape, one small TraceImporter protocol per source. None of the three are verified against a live export from a real account (no account access) — each module's own docstring says exactly what's confirmed vs. representative-but-unverified, rather than overclaiming.
    • [x] codegen/test_writer.py — graphtrace from-trace. Two real design gaps found and fixed while building this, not assumed away:
      1. An imported trace's request field can never hash-match the real str(list[BaseMessage]) the live LangGraph interceptor hashes at replay time (different platforms serialize completely differently) — replay/engine.py gained a position-only fallback match (node/kind/any/occurrence), scoped so it can never shadow a real recorded cassette entry.
      2. A generated test originally asserted the exact path (assert_path) from the trace's spans — but spans only capture LLM/tool calls, so a node that makes neither (a routing branch, an interrupt point) is invisible to every importer. Asserting an exact path from that would be a false promise; the generated test now asserts assert_visited per node that made a captured call instead, with a TODO pointing at assert_path/assert_tool_calls_match for tightening it by hand. Also: a factory requiring arguments (this project's own build_refund_graph(chat_model, ...) is written exactly that way) is now detected by actually importing --target and inspecting its signature, rather than assuming every factory is zero-argument.
    • [x] report/results.py, report/html.py — TestResult (JSON-safe by construction), Jinja2 autoescape=True (confirmed with a real XSS test: trajectory state containing <script> renders escaped). Verified against a real run_graph() Trajectory from the Week 1 demo agent, not just a hand-built one.
    • [x] plugin.py extended: --gt-report=<path> collects a TestResult per test (including a distinct "error" outcome for a test whose fixture failed before the body ran) and renders the HTML report — plus a results.json alongside it — at session end.
    • [x] cli.py, [project.scripts] — a real graphtrace console command: from-trace, calibrate, report. The actual verify-by: a real Langfuse-shaped trace fixture, run through graphtrace from-trace for real, produces a generated test file that a real pytest --gt-mode=replay subprocess run then passes — checked end to end, not just that generate_test() returns some string.
    • [x] .github/workflows/graphtrace.yml — pytest + mkdocs build --strict on every push/PR, both confirmed green locally before committing to the claim.

    169 tests pass today, full regression. See Judge & calibration, Trace-to-test, Report & CI, and the CLI reference.

    Real-world readiness hardening (2026-10-26)¶

    Not a new build-plan week — a deliberate pass asking "is this actually ready to validate against a real application?" and closing every gap the honest answer surfaced, rather than letting "169 tests pass" stand in for real-world readiness. 178 tests pass after this pass, full regression (~30s with the live Groq tests included, ~25s without — see below).

    • The judge, verified against a real provider for the first time. GROQ_API_KEY (real, working) + a real graphtrace.yaml/rubrics/refund_reply.yaml/evals/calibration.jsonl (a small, 4-case, hand-authored demonstration set, honestly not the 20-50 cases a production threshold needs). tests/test_judge_live.py (4 tests, skips cleanly without the key, same pattern as kbguard's live Pinecone test) proves grade()/calibrate() work against a real groq/openai/gpt-oss-120b model, including that a replayed cassette genuinely never calls the judge again — the fake-litellm tests already covered the shape of this; this covers whether it's actually true.
    • A real, previously-undetected recorder bug: subgraphs. Step.kind's "subgraph_enter"/"subgraph_exit" existed in the type since Week 1 but were never actually produced — nothing tested a node whose value is itself a compiled graph. Investigated by hand against a real nested graph (confirmed: a subgraph's own inner checkpoints are tagged with a deeper namespace, and chain langgraph_checkpoint_ns correctly, so LLM/tool-call attribution already worked). What didn't: the recorder's last_values/pending-task bookkeeping was global, single-namespace state, so a subgraph running concurrently with another outer-level node could have the sibling's state_after committed early using the subgraph's own unrelated partial state — reproduced by hand, then fixed by scoping that bookkeeping per namespace, and by actually emitting subgraph_enter/subgraph_exit (transparently exposing the subgraph's own inner nodes, rather than collapsing it to one step and silently losing their LLM/tool calls). Both failure modes are now regression tests in tests/test_runner.py, each confirmed to genuinely fail against the pre-fix code before trusting them.
    • Packaging, actually checked this time. A real wheel build (python -m build), twine check (passed), and inspection confirmed report/templates/report.html.j2 is bundled by hatchling's default rules — the Week 4 concern noted here previously turned out to be a non-issue, but only checking it that way earns believing it. Installed into a venv with its own python.exe invoked directly (the first attempt used source .../activate, which silently resolved to the system Python instead of the venv's — caught before it invalidated the test) and confirmed the console script, python -m graphtrace.cli, and the pytest11 entry point all work from a wheel-only install with nothing else on the path.
    • Trace importers, checked against real upstream sources, not just documentation summaries. Fetched and quoted the real openinference-semantic-conventions source directly: found that llm.input_messages/llm.output_messages are never literal attribute keys at all (messages are flattened per-index, llm.input_messages.0.message.content/.role) — importers/otel.py's old fallback read a key that could never match anything in a real export, silently falling through to input.value every time. Fixed with real per-index reconstruction, which surfaced a second bug one level up: codegen/test_writer.py's _normalize_llm_response would have stringified that reconstructed message list wholesale ("[{'role': ...}]") instead of extracting the actual reply text — fixed to extract the last message's content, the way a real AIMessage.content would read. importers/langsmith.py's field names (run_type/inputs/outputs/start_time/end_time/name) were independently re-confirmed against the real SDK's own RunTree test file and the official run-data-format doc; where the model name actually lives for an llm run genuinely isn't documented anywhere (confirmed by checking, not just not-knowing) and stays an honestly-flagged gap. importers/langfuse.py's observation field names were independently re-confirmed against the real, current GET /api/public/v2/observations API reference. None of the three importers have still been run against a live account export -- that specific gap needs real account access, which checking public API docs and SDK source can't substitute for.

    Real-world validation: a real external app (2026-10-26, same day)¶

    Everything above was verified against this project's own demo agent, hand-written specifically to exercise graphtrace's own features. This pass pointed run_graph() at a real, official, external app instead — langchain-ai/langgraph-swarm-py (the LangGraph team's own multi-agent swarm library, MIT, ~1.6k stars) — and found three more real bugs, none of which the demo agent had ever been capable of exercising. tests/test_langgraph_swarm_compat.py keeps this as a permanent, real (not hand-approximated) regression test, gated behind the dev extra's new langgraph-swarm dependency with pytest.importorskip.

    1. LangChain 1.x's create_agent() doesn't thread an explicit config into its model call. Confirmed by hand that BaseChatModel.invoke() receives config=None every time under this newer agent abstraction — every call was attributed to node "?" instead of the real node name, because the explicit-config lookup this project's interceptors relied on since Week 1 simply had nothing to read. The real metadata was still there, just reachable only through LangChain's own ambient, contextvar-based config propagation (langchain_core.runnables.config). Fixed by resolving metadata through ensure_config(config) (the same public function LangChain's own runnables use for exactly this fallback) instead of reading config directly — what's forwarded to the real underlying call is untouched either way.
    2. A subgraph's subgraph_enter/subgraph_exit step pair had their index values backwards. Yesterday's subgraph fix created a new step for the enter marker with a fresh (later) index, while the exit marker kept the parent's original (earlier) one — exit showing a lower number than its own enter. Fixed by swapping which step plays which role: the parent's original, early-indexed step becomes the enter marker; a new step, indexed at detection time (always later), becomes the eventual exit.
    3. A tool call returning Command(graph=Command.PARENT, ...) — LangGraph's own real handoff mechanism — never gets its own task_result/checkpoint event at all. Confirmed against the real debug-event stream: the child task's completion folds directly into the parent's own task_result, with no settling point for the child in between. Without a fix, that step would simply never commit — not even via flush()'s existing "no checkpoint is ever coming" fallback, since a different event (the parent's own resolution) is what actually signals it's over. Fixed by absorbing any task still pending directly under a resolving task's own namespace the instant that happens. A closely related second bug surfaced at the same time: neither the tool's real args (which can carry an entire injected graph state, including raw BaseMessage objects — LangGraph's own "inject full state as a tool arg" pattern) nor a real Command result were YAML-safe, crashing cassette writes outright. Fixed with a generic, recursive serializer (_yaml_safe/_restore_value) that round-trips BaseMessage (human/ai/tool/system) and Command correctly through replay — not just avoiding a crash, but handing back a real Command object on replay, since a real node's own isinstance(result, Command) check would otherwise silently fail against a plain dict.

    181 tests pass today. A real HTML report from this run (graphtrace report, both tests, record and replay, the real Command/handoff mechanics visible in the trajectory tree) was generated and shared directly, not just described.

    Executive summary for the HTML report (2026-10-27)¶

    Shown the real HTML report, the honest answer to "who reads this" was: an engineer debugging a failed test, full stop — raw Python reprs, internal jargon (subgraph_enter, node='?'), stack-trace-style error strings. Nothing in it served a QA lead, a manager, a consultant, or an auditor deciding go/no-go, even though those are exactly the roles a release-readiness report needs to serve.

    Added a layer above the existing trajectory detail, not a replacement for it:

    • @pytest.mark.graphtrace(description=..., severity=..., category=...) — optional, human-authored metadata a test author attaches directly to a test. Graphtrace has no way to know on its own that "refunded without approval" is more severe than "wording changed slightly" — that's a judgment call only a human can make, and this is where it's recorded. All three default cleanly (severity to "normal", the others to None) so an untagged test still reports correctly; adopting this is additive, never required first.
    • A release verdict — READY or NOT READY, N blocking issues — computed from plain pass/fail, always meaningful regardless of whether anything was tagged.
    • Blocking issues, ranked by severity (critical first), each showing its plain-language description (or the bare test id, honestly, if none was given) and its category, linking down to the existing technical detail for whoever needs to debug it. Severity never decides whether a failure blocks — only how it's ranked and emphasized among real ones; graphtrace never gets to decide a failure is "safe to ship anyway."
    • A coverage breakdown by category — what was actually tested, not just how many things passed. Says so honestly (coverage breakdown unavailable) when nothing was tagged, rather than fabricating one from test names.
    • The existing per-test trajectory tree, judge verdicts, and raw calls are unchanged, just moved under a collapsed <details> disclosure — still there for an engineer, no longer the first (or only) thing anyone sees.

    Deliberately not attempted: a trend view across multiple runs ("better or worse than last time"). That needs a separate persistence design (where history lives, how many runs to keep, per-branch or not) that wasn't designed, let alone built, here — flagged honestly rather than half-built.

    examples/sample_report/ regenerated to actually demonstrate this (real descriptions/severities/categories on all three sample results, not the bare-test-id fallback). 199 tests pass today.

    Second real-world validation: langchain-ai/deepagents (2026-10-27)¶

    A second real, official app — langchain-ai/deepagents (~30.6k stars, the highest-profile target researched), whose own README documents "any LangGraph CompiledStateGraph can be passed in as a sub-agent." Deliberately a different way of using a subgraph than langgraph-swarm-py's: there, "Alice"/"Bob" are direct nodes of the swarm's own compiled graph; here, the sub-agent is invoked from inside a plain tool function (task), not added as a graph node at all — different enough to surface a fourth real bug and one genuine structural limitation, neither of which the first app's testing could have.

    1. ToolRuntime (LangChain's dependency-injection object, given to a tool that declares a runtime: ToolRuntime parameter) carries the entire live Pregel execution state as its config field — per-run object ids, open file/thread handles, functools.partials. Confirmed by hand that this made the recorded cassette entry for the exact same logical call hash differently across two genuinely separate processes (default object reprs embed memory addresses), on top of bloating the cassette into something unreadable — and, found a step later while actually generating a report from it, the same raw dump was landing directly in the in-memory Trajectory itself (ToolCall.args), not just the cassette, since only the copy passed to the cassette writer had been sanitized. Fixed in both places: _yaml_safe() now recognizes ToolRuntime (lazily imported from the full langchain package, never a hard dependency) and keeps only state and tool_call_id — the only parts a human reading a cassette, or a hash matching two calls, could plausibly care about.
    2. A real, structural limitation, not a bug: a tool whose own implementation triggers a nested LangGraph execution (deepagents' task tool really does call compiled_subagent.invoke(...) inside its own Python body) loses that nested execution's own step-by-step visibility in replay mode. Confirmed by hand that record mode shows the sub-agent's own nested model step (the same subgraph_enter/exit mechanism that already handles a subgraph node), while replay mode shows only the single, opaque, cached task tool call — replaying it means the real tool body, including its own compiled_subagent.invoke(...) call, genuinely never executes. The parent's own real-world outcome (its final message) is identical either way; only the fine-grained trace of how the sub-agent itself got there is unrecoverable once that specific call is served from a cassette. Documented, not patched around — a real fix would mean recursively intercepting calls made from inside an already-intercepted call, a genuinely different and larger feature, not a quick correction.

    Kept as a permanent regression test, tests/test_deepagents_compat.py (gated with pytest.importorskip, deepagents added as a second dev-extra compatibility dependency), including a real assertion for the limitation itself (record mode's trajectory has nested steps; replay mode's doesn't; both reach the identical final message) rather than leaving it as prose that could silently go stale.

    201 tests pass today. A real HTML report covering both external apps was generated and shared directly.

    Real-world test depth (2026-10-27, same day)¶

    Asked directly, looking at the shared report: can 3 thin, mostly happy-path tests actually justify a "READY" verdict? No — and that's exactly the overclaiming problem the executive summary work above exists to prevent, not produce. Three real additional scenarios added, using these libraries' own real test patterns again (not invented), so the coverage breakdown means something instead of showing one category once:

    • Parallel sub-agent delegation — the real pattern from deepagents' own test_multiple_subagents_invoked_in_parallel: two different sub-agents invoked concurrently from a single parent message, each completing independently with its own distinct result, confirmed not conflated or dropped.
    • A real safety property: delegating to a sub-agent type that was never registered. Confirmed the parent recovers gracefully (a normal tool result it can act on, not a crash) and that the named sub-agent's own model genuinely never ran — checked directly against the fake model's own call history, not inferred from the trajectory alone.
    • A real assert_budget check — fast and local (no real network at all) specifically so the threshold tests "did graphtrace's own interception add unreasonable overhead," not "was the network slow today."

    The two langgraph-swarm-py tests were also given real categories (handoff, tool_use) they'd been missing. The report's coverage breakdown across both real apps now reads handoff, tool_use, delegation, parallel_execution, safety, performance — six distinct real dimensions, not three thin ones labeled once.

    204 tests pass today.

    Real-world test depth, round two (2026-10-27, same day)¶

    Asked again, more pointedly: "still only 7? can it be made of 30-50 cases?" The honest answer wasn't to pad the existing happy-path flows with reworded copies — it was to go back to both libraries' own real test suites for scenarios this project hadn't touched yet, mining deepagents' own test_file_system_tools.py, test_permissions.py, and test_todo_middleware.py, plus a few new variations built directly against the public APIs already in use (a longer swarm handoff chain, a real tool exception, extended checkpointer persistence). The real count landed at 25 real-app scenarios, not 30-50 — documented here plainly rather than padded to hit a round number that wouldn't mean anything.

    tests/test_deepagents_filesystem_compat.py (new, 10 tests) — deepagents' own built-in filesystem tools (write_file, edit_file, grep, ls, delete), exercised through a full create_deep_agent() graph instead of calling backend internals directly:

    • write_file → edit_file (single replacement and replace_all), each on a real StateBackend-stored file.
    • edit_file failing gracefully on a missing file and on a missing search string — both real backend error strings, not exceptions escaping to the caller.
    • grep finding content written by two files created in parallel tool calls in a single AIMessage.
    • ls listing a freshly written file, then delete removing it — confirmed gone.
    • Four real path-traversal/safety checks (severity="high"): edit_file/read_file/write_file/ls all reject ../ traversal, a bare Windows absolute path, and a ~-prefixed path, with the real backend error string, not a crash.

    One real test-authoring correction along the way, not a graphtrace bug: these tools run through LangGraph's real ToolNode, which wraps a tool's plain string return into a real ToolMessage — ToolCall.result is that ToolMessage, so assertions need .content, not a direct string comparison (already correctly handled on the serialization side; the new tests had just assumed the wrong shape at first).

    tests/test_deepagents_permissions_todo_compat.py (new, 5 tests) — two more of deepagents' own real middleware features, FilesystemPermission write/delete enforcement and TodoListMiddleware, both driven through a full agent conversation instead of deepagents' own unit-level internal-function tests:

    • A write_file call denied by a FilesystemPermission(mode="deny") rule, and the identical rule set having no effect on a write outside its path (severity="high" / contrast case).
    • The real all-or-nothing recursive-delete behavior from deepagents' own TestRecursiveDeletePermissions: deleting a directory is refused whenever any file beneath it is write-denied, even if most of the subtree is unrestricted (severity="high").
    • TodoListMiddleware (not in create_deep_agent's default stack — added via its own documented middleware=[...] merge point) tracking a single write_todos call in final_state["todos"].
    • A second real structural gap, distinct from the nested-subgraph-visibility one found testing deepagents the first time: the real scenario copied from deepagents' own test_todo_middleware.py (two write_todos calls in the same AIMessage must both be rejected) revealed that TodoListMiddleware's wrap_tool_call rejection happens before graphtrace's patched BaseTool.invoke/ainvoke ever fires — traj.tool_calls is empty for both rejected calls, even though the real conversation (final_state["messages"]) carries both real error ToolMessages with the exact real error text, and todos correctly stays unset. The agent's own behavior is completely unaffected; only Trajectory.tool_calls undercounts in this one case. Documented with a real, verified assertion (assert not any(c.name == "write_todos" for c in traj.tool_calls)) rather than left as prose.

    tests/test_langgraph_swarm_compat.py (3 new tests, 5 total) — three more real scenarios built directly against langgraph-swarm-py's own create_swarm/create_handoff_tool/create_agent API, verified by hand before being written:

    • A three-agent handoff chain (Alice → Bob → Carol), confirming the subgraph enter/exit fix from the first langgraph-swarm-py pass holds across more than one hop, not just the original two-agent case.
    • A real tool exception (ZeroDivisionError from a real divide tool) propagating through run_graph() with its exact real type uncorrupted — the first time this project's own documented "a live exception keeps its real type" guarantee was confirmed against a real external app's real tool error, not graphtrace's own synthetic demo agent.
    • State persisting across three conversation turns, not just two — active_agent surviving a second full handoff-and-back round trip on the same checkpointer-backed thread.

    222 tests pass today. The report's coverage breakdown now spans ten real categories across two real external apps: handoff, tool_use, error_handling, state_persistence, delegation, parallel_execution, safety, performance, planning — real distinct dimensions of real library behavior, not reworded restatements of the same two flows.

    v0.2 — not started, not scheduled for v0.1¶

    Four pieces, all building on the already-shipped core rather than needing new infrastructure: the security test pack (scope), observability export (scope), cut-point replay (adopted from Chronicle, Microsoft, arXiv 2609.20625 — replay a recorded incident up to where it broke, then run the fix live from there), and statistical live-mode verification (adopted from AgentAssay, arXiv 2603.02601 — a Wilson-interval Pass/Fail/Inconclusive verdict across N real trials, so a single flaky nightly run stops being the whole story; see Recording & replay).

    v0.4 — not started, not scheduled for v0.1-v0.3¶

    CrewAI and AutoGen support (scope) — gated on v0.1 shipping first. Unlike v0.2's two features, this one required a real architecture decision made now, in v0.1: runtime/ was never built as a flat, LangGraph-only package — it's frameworks/base.py (a shared Protocol) + frameworks/langgraph/ from day one, so CrewAI/AutoGen land as new sibling packages in v0.4, not a rename of something already shipped.
