## Week 1 — foundations

**Goal (per the build plan):** plugin entry point, `Trajectory`, recorder, `run_graph`, core assertions, demo agent — 10 tests on a demo agent passing in live mode.

**Status: met (2026-10-22).** Both halves are done and verified: the framework-agnostic data model/assertion API, and the LangGraph-specific recorder/runner/interceptors/plugin/demo agent.

- [x] `core/trajectory.py` — `LLMCall`, `ToolCall`, `Step`, `Trajectory` dataclasses plus derived properties (`path`, `visits`, `tool_calls`, `llm_calls`, `final_message`, `cost_usd`, `latency_s`, `tokens_total`). Deliberate fix versus the original architecture plan: `cost_usd` is a field precomputed per `LLMCall`, not something `Trajectory` computes by reaching into a pricing table — the original plan would have made `core` depend on the LangGraph-specific layer, breaking the project's own layering rule. 7 tests, see [Core concepts](../guide/trajectory-model.md).
- [x] `core/errors.py` — `TrajectoryAssertionError` (subclasses `AssertionError` so `pytest.raises(AssertionError)` still catches it) plus an index-by-index path diff formatter, so a path mismatch reads as a diff, not two dumped lists.
- [x] `core/matchers.py` — `any_str()`, the one matcher the architecture plan actually names; a `Matcher` base class ready for more the day a real test needs one.
- [x] `core/assertions.py` — all 12 `assert_*` functions. Two deliberate scope decisions versus the original plan, both documented on [Assertions](../guide/assertions.md): `assert_path`'s `...` gap supports exactly one gap (a second raises `ValueError` rather than guessing which gap a mismatch belongs to), and `assert_retries` specifically means "a node re-entered after one of its own tool calls errored," not just "visited more than once" — distinct from `assert_visits`. The 12th, `assert_tool_calls_match`, is adopted deliberately from `langchain-ai/agentevals`' own trajectory-match evaluator (strict/unordered/subset/superset modes) rather than invented. 30 tests.
- [x] `frameworks/base.py` — the `FrameworkRunner` Protocol, built *before* the LangGraph implementation below. Added to the plan on 2026-10-21 specifically so v0.4's CrewAI/AutoGen support (see [Multi-framework support](../guide/multi-framework.md)) is a new package later, not a refactor of a shipped one. `src/graphtrace/py.typed` added alongside it (PEP 561 marker, so the Protocol type-checks for an external implementer) — proactively, since this project has no `mypy` wired up yet to actually confirm the Protocol is satisfied correctly; see [Contributing](contributing.md).
- [x] `frameworks/pricing.py` — token → USD table, sets `LLMCall.cost_usd` at record time.
- [x] `frameworks/langgraph/interceptors.py` — patches `BaseChatModel.invoke`/`ainvoke` and `BaseTool.invoke`/`ainvoke`. **Corrected from the original plan's `_generate`/`_run`**: every concrete chat model (OpenAI's, Anthropic's, LangChain's own `GenericFakeChatModel`) overrides `_generate` itself, so patching the base class's version intercepts nothing real — confirmed by hand before trusting it. Attribution uses `config["metadata"]["langgraph_checkpoint_ns"]` (a `"{node}:{task_id}"` string LangGraph itself attaches), **not** the originally-planned `contextvars` — a ContextVar set while consuming the event stream doesn't survive into the `ThreadPoolExecutor` worker thread LangGraph actually runs parallel nodes on, confirmed with a `threading.current_thread()` probe before relying on it.
- [x] `frameworks/langgraph/recorder.py` — turns LangGraph's `debug` stream into `Step`s (subscribing to `debug` alone; `updates` turned out to duplicate `task_result.result` exactly). Added a `flush()` step and resume-dedup logic beyond the original design: a step paused on an interrupt never gets a settling `checkpoint` event, and resuming re-runs it under the *same* task id, which would otherwise show up as a duplicate.
- [x] `frameworks/langgraph/runner.py` — `run_graph()` and `arun_graph()`.
- [x] `plugin.py` — pytest entry point (`pytest11`), `run_graph` fixture. Scope reduced from the original plan: `--gt-mode` and the `cassette`/`judge` fixtures aren't added yet since they'd do nothing today.
- [x] `examples/refund_agent/` — a demo agent to record and assert against for real. Writing its tests caught a real bug in the agent itself: `refund` unconditionally refunded regardless of whether the human approved, a missing conditional edge.

Not a new build-plan week — a deliberate pass asking "is this actually ready to validate against a real application?" and closing every gap the honest answer surfaced, rather than letting "169 tests pass" stand in for real-world readiness. **178 tests pass after this pass**, full regression (~30s with the live Groq tests included, ~25s without — see below).

- **The judge, verified against a real provider for the first time.** `GROQ_API_KEY` (real, working) + a real `graphtrace.yaml`/`rubrics/refund_reply.yaml`/`evals/calibration.jsonl` (a small, 4-case, hand-authored *demonstration* set, honestly not the 20-50 cases a production threshold needs). `tests/test_judge_live.py` (4 tests, skips cleanly without the key, same pattern as kbguard's live Pinecone test) proves `grade()`/`calibrate()` work against a real `groq/openai/gpt-oss-120b` model, including that a replayed cassette genuinely never calls the judge again — the fake-`litellm` tests already covered the *shape* of this; this covers whether it's actually true.
- **A real, previously-undetected recorder bug: subgraphs.** `Step.kind`'s `"subgraph_enter"`/`"subgraph_exit"` existed in the type since Week 1 but were never actually produced — nothing tested a node whose value is itself a compiled graph. Investigated by hand against a real nested graph (confirmed: a subgraph's own inner checkpoints are tagged with a deeper namespace, and chain `langgraph_checkpoint_ns` correctly, so LLM/tool-call attribution already worked). What didn't: the recorder's `last_values`/pending-task bookkeeping was global, single-namespace state, so a subgraph running *concurrently* with another outer-level node could have the sibling's `state_after` committed early using the subgraph's own unrelated partial state — reproduced by hand, then fixed by scoping that bookkeeping per namespace, and by actually emitting `subgraph_enter`/`subgraph_exit` (transparently exposing the subgraph's own inner nodes, rather than collapsing it to one step and silently losing their LLM/tool calls). Both failure modes are now regression tests in `tests/test_runner.py`, each confirmed to genuinely fail against the pre-fix code before trusting them.
- **Packaging, actually checked this time.** A real wheel build (`python -m build`), `twine check` (passed), and inspection confirmed `report/templates/report.html.j2` *is* bundled by hatchling's default rules — the Week 4 concern noted here previously turned out to be a non-issue, but only checking it that way earns believing it. Installed into a venv with its own `python.exe` invoked directly (the first attempt used `source .../activate`, which silently resolved to the *system* Python instead of the venv's — caught before it invalidated the test) and confirmed the console script, `python -m graphtrace.cli`, and the `pytest11` entry point all work from a wheel-only install with nothing else on the path.
- **Trace importers, checked against real upstream sources, not just documentation summaries.** Fetched and quoted the real `openinference-semantic-conventions` source directly: found that `llm.input_messages`/`llm.output_messages` are never literal attribute keys at all (messages are flattened per-index, `llm.input_messages.0.message.content`/`.role`) — `importers/otel.py`'s old fallback read a key that could never match anything in a real export, silently falling through to `input.value` every time. Fixed with real per-index reconstruction, which surfaced a second bug one level up: `codegen/test_writer.py`'s `_normalize_llm_response` would have stringified that reconstructed message list wholesale (`"[{'role': ...}]"`) instead of extracting the actual reply text — fixed to extract the last message's content, the way a real `AIMessage.content` would read. `importers/langsmith.py`'s field names (`run_type`/`inputs`/`outputs`/`start_time`/`end_time`/`name`) were independently re-confirmed against the real SDK's own `RunTree` test file and the official run-data-format doc; where the model name actually lives for an `llm` run genuinely isn't documented anywhere (confirmed by checking, not just not-knowing) and stays an honestly-flagged gap. `importers/langfuse.py`'s observation field names were independently re-confirmed against the real, current `GET /api/public/v2/observations` API reference. ## Real-world validation: a real external app (2026-10-26, same day)

Everything above was verified against this project's own demo agent, hand-written specifically to exercise graphtrace's own features. This pass pointed `run_graph()` at a real, official, external app instead — [`langchain-ai/langgraph-swarm-py`](https://github.com/langchain-ai/langgraph-swarm-py) (the LangGraph team's own multi-agent swarm library, MIT, ~1.6k stars) — and found **three more real bugs**, none of which the demo agent had ever been capable of exercising. `tests/test_langgraph_swarm_compat.py` keeps this as a permanent, real (not hand-approximated) regression test, gated behind the `dev` extra's new `langgraph-swarm` dependency with `pytest.importorskip`.

1. **LangChain 1.x's `create_agent()` doesn't thread an explicit `config` into its model call.** Confirmed by hand that `BaseChatModel.invoke()` receives `config=None` every time under this newer agent abstraction — every call was attributed to node `"?"` instead of the real node name, because the explicit-config lookup this project's interceptors relied on since Week 1 simply had nothing to read. The real metadata was still there, just reachable only through LangChain's own *ambient*, contextvar-based config propagation (`langchain_core.runnables.config`). Fixed by resolving metadata through `ensure_config(config)` (the same public function LangChain's own runnables use for exactly this fallback) instead of reading `config` directly — what's forwarded to the real underlying call is untouched either way.
2. **A subgraph's `subgraph_enter`/`subgraph_exit` step pair had their `index` values backwards.** Yesterday's subgraph fix created a *new* step for the enter marker with a fresh (later) index, while the exit marker kept the parent's original (earlier) one — exit showing a lower number than its own enter. Fixed by swapping which step plays which role: the parent's original, early-indexed step becomes the enter marker; a new step, indexed at detection time (always later), becomes the eventual exit.
3. **A tool call returning `Command(graph=Command.PARENT, ...)` — LangGraph's own real handoff mechanism — never gets its own `task_result`/checkpoint event at all.** Confirmed against the real debug-event stream: the child task's completion folds directly into the *parent's* own `task_result`, with no settling point for the child in between. Without a fix, that step would simply never commit — not even via `flush()`'s existing "no checkpoint is ever coming" fallback, since a *different* event (the parent's own resolution) is what actually signals it's over. Fixed by absorbing any task still pending directly under a resolving task's own namespace the instant that happens. A closely related second bug surfaced at the same time: neither the tool's real `args` (which can carry an entire injected graph state, including raw `BaseMessage` objects — LangGraph's own "inject full state as a tool arg" pattern) nor a real `Command` result were YAML-safe, crashing cassette writes outright. Fixed with a generic, recursive serializer (`_yaml_safe`/`_restore_value`) that round-trips `BaseMessage` (human/ai/tool/system) and `Command` correctly through replay — not just avoiding a crash, but handing back a *real* `Command` object on replay, since a real node's own `isinstance(result, Command)` check would otherwise silently fail against a plain dict.

**181 tests pass today.** A real HTML report from this run (`graphtrace report`, both tests, record and replay, the real `Command`/handoff mechanics visible in the trajectory tree) was generated and shared directly, not just described.

## Executive summary for the HTML report (2026-10-27)

Shown the real HTML report, the honest answer to "who reads this" was: an engineer debugging a failed test, full stop — raw Python reprs, internal jargon (`subgraph_enter`, `node='?'`), stack-trace-style error strings. Nothing in it served a QA lead, a manager, a consultant, or an auditor deciding go/no-go, even though those are exactly the roles a release-readiness report needs to serve.

Added a layer *above* the existing trajectory detail, not a replacement for it:

- **`@pytest.mark.graphtrace(description=..., severity=..., category=...)`** — optional, human-authored metadata a test author attaches directly to a test. Graphtrace has no way to know on its own that "refunded without approval" is more severe than "wording changed slightly" — that's a judgment call only a human can make, and this is where it's recorded. All three default cleanly (`severity` to `"normal"`, the others to `None`) so an untagged test still reports correctly; adopting this is additive, never required first.
- **A release verdict** — **READY** or **NOT READY, N blocking issues** — computed from plain pass/fail, always meaningful regardless of whether anything was tagged.
- **Blocking issues, ranked by severity** (critical first), each showing its plain-language description (or the bare test id, honestly, if none was given) and its category, linking down to the existing technical detail for whoever needs to debug it. Severity never decides *whether* a failure blocks — only how it's ranked and emphasized among real ones; graphtrace never gets to decide a failure is "safe to ship anyway."
- **A coverage breakdown** by category — what was actually tested, not just how many things passed. Says so honestly (`coverage breakdown unavailable`) when nothing was tagged, rather than fabricating one from test names.
- The existing per-test trajectory tree, judge verdicts, and raw calls are unchanged, just moved under a collapsed `<details>` disclosure — still there for an engineer, no longer the first (or only) thing anyone sees.

**Deliberately not attempted**: a trend view across multiple runs ("better or worse than last time"). That needs a separate persistence design (where history lives, how many runs to keep, per-branch or not) that wasn't designed, let alone built, here — flagged honestly rather than half-built.

`examples/sample_report/` regenerated to actually demonstrate this (real descriptions/severities/categories on all three sample results, not the bare-test-id fallback). **199 tests pass today.**

## Second real-world validation: `langchain-ai/deepagents` (2026-10-27)

A second real, official app — [`langchain-ai/deepagents`](https://github.com/langchain-ai/deepagents) (~30.6k stars, the highest-profile target researched), whose own README documents "any LangGraph `CompiledStateGraph` can be passed in as a sub-agent." Deliberately a *different* way of using a subgraph than `langgraph-swarm-py`'s: there, "Alice"/"Bob" are direct nodes of the swarm's own compiled graph; here, the sub-agent is invoked *from inside* a plain tool function (`task`), not added as a graph node at all — different enough to surface a fourth real bug and one genuine structural limitation, neither of which the first app's testing could have.

1. **`ToolRuntime` (LangChain's dependency-injection object, given to a tool that declares a `runtime: ToolRuntime` parameter) carries the entire live Pregel execution state as its `config` field** — per-run object ids, open file/thread handles, `functools.partial`s. Confirmed by hand that this made the recorded cassette entry for the *exact same logical call* hash differently across two genuinely separate processes (default object reprs embed memory addresses), on top of bloating the cassette into something unreadable — and, found a step later while actually generating a report from it, the *same* raw dump was landing directly in the in-memory `Trajectory` itself (`ToolCall.args`), not just the cassette, since only the copy passed to the cassette writer had been sanitized. Fixed in both places: `_yaml_safe()` now recognizes `ToolRuntime` (lazily imported from the full `langchain` package, never a hard dependency) and keeps only `state` and `tool_call_id` — the only parts a human reading a cassette, or a hash matching two calls, could plausibly care about.
2. **A real, structural limitation, not a bug**: a tool whose own implementation triggers a nested LangGraph execution (deepagents' `task` tool really does call `compiled_subagent.invoke(...)` inside its own Python body) loses that nested execution's own step-by-step visibility in replay mode. Confirmed by hand that record mode shows the sub-agent's own nested `model` step (the same `subgraph_enter`/`exit` mechanism that already handles a subgraph *node*), while replay mode shows only the single, opaque, cached `task` tool call — replaying it means the real tool body, including its own `compiled_subagent.invoke(...)` call, genuinely never executes. The parent's own real-world outcome (its final message) is identical either way; only the fine-grained trace of *how the sub-agent itself got there* is unrecoverable once that specific call is served from a cassette. Documented, not patched around — a real fix would mean recursively intercepting calls made from inside an already-intercepted call, a genuinely different and larger feature, not a quick correction.

Kept as a permanent regression test, `tests/test_deepagents_compat.py` (gated with `pytest.importorskip`, `deepagents` added as a second `dev`-extra compatibility dependency), including a real assertion for the limitation itself (record mode's trajectory has nested steps; replay mode's doesn't; both reach the identical final message) rather than leaving it as prose that could silently go stale.

**201 tests pass today.** A real HTML report covering both external apps was generated and shared directly.

## Real-world test depth (2026-10-27, same day)

Asked directly, looking at the shared report: can 3 thin, mostly happy-path tests actually justify a "READY" verdict? No — and that's exactly the overclaiming problem the executive summary work above exists to prevent, not produce. Three real additional scenarios added, using these libraries' own real test patterns again (not invented), so the coverage breakdown means something instead of showing one category once:

- **Parallel sub-agent delegation** — the real pattern from deepagents' own `test_multiple_subagents_invoked_in_parallel`: two different sub-agents invoked concurrently from a single parent message, each completing independently with its own distinct result, confirmed not conflated or dropped.
- **A real safety property**: delegating to a sub-agent type that was never registered. Confirmed the parent recovers gracefully (a normal tool result it can act on, not a crash) *and* that the named sub-agent's own model genuinely never ran — checked directly against the fake model's own call history, not inferred from the trajectory alone.
- **A real `assert_budget` check** — fast and local (no real network at all) specifically so the threshold tests "did graphtrace's own interception add unreasonable overhead," not "was the network slow today."

The two `langgraph-swarm-py` tests were also given real categories (`handoff`, `tool_use`) they'd been missing. The report's coverage breakdown across both real apps now reads `handoff`, `tool_use`, `delegation`, `parallel_execution`, `safety`, `performance` — six distinct real dimensions, not three thin ones labeled once.

Four pieces, all building on the already-shipped core rather than needing new infrastructure: the security test pack ([scope](../guide/security-test-pack.md)), observability export ([scope](../guide/observability-export.md)), [cut-point replay](../guide/cut-point-replay.md) (adopted from Chronicle, Microsoft, arXiv 2609.20625 — replay a recorded incident up to where it broke, then run the fix live from there), and statistical live-mode verification (adopted from AgentAssay, arXiv 2603.02601 — a Wilson-interval Pass/Fail/Inconclusive verdict across N real trials, so a single flaky nightly run stops being the whole story; see [Recording & replay](../guide/recording-and-replay.md#statistical-live-mode-verification-v02)).

## v0.4 — not started, not scheduled for v0.1-v0.3

CrewAI and AutoGen support ([scope](../guide/multi-framework.md)) — gated on v0.1 shipping first. Unlike v0.2's two features, this one required a real architecture decision made *now*, in v0.1: `runtime/` was never built as a flat, LangGraph-only package — it's `frameworks/base.py` (a shared Protocol) + `frameworks/langgraph/` from day one, so CrewAI/AutoGen land as new sibling packages in v0.4, not a rename of something already shipped.
