### Fixed (2026-10-26) -- found by checking real sources, not by re-reading docs
- **A real recorder bug: subgraph bookkeeping was global, single-namespace state.** `frameworks/langgraph/recorder.py`'s `last_values`/pending-task tracking was shared across every namespace. Harmless for a subgraph running alone (the outer graph's own next checkpoint always arrives later and corrects it before anything reads it again), but reproduced by hand: a subgraph running *concurrently* with another outer-level node (parallel fan-out) could commit that sibling's `state_after` early, using the subgraph's own unrelated partial state instead of the outer graph's. Fixed by scoping `last_values`/pending tasks/awaiting-commit list/committed-by-id per namespace -- a pure addition for the outer namespace `()`, which behaves identically to before (it's the only namespace that existed prior to subgraphs).
- **`Step.kind`'s `"subgraph_enter"`/`"subgraph_exit"` were declared in the type (since Week 1) but never actually produced.** Nothing in the recorder ever set a step's kind to either value -- a subgraph-wrapping node's own task/task_result pair looks identical in shape to an ordinary node's. Fixed: the recorder now detects a subgraph (a *child* event arriving at a namespace that extends a pending task's) and emits a `subgraph_enter` step immediately (so it appears before its children in the path) plus a `subgraph_exit` step when the wrapping task's own checkpoint finally arrives (necessarily last). The alternative -- collapsing the whole subgraph into one opaque step -- was considered and rejected: confirmed by hand that a call made *inside* a subgraph's own node is attributed to that inner node's task id, never the wrapper's, so collapsing it would have silently dropped those LLM/tool calls from the trajectory entirely.
- **`importers/otel.py` read an attribute key that can never exist in a real export.** Fetched and quoted `openinference-semantic-conventions`'s own source directly: there is no single `"llm.input_messages"` attribute -- chat messages are flattened per-index (`llm.input_messages.0.message.content`/`.role`, `.1....`). The old fallback silently never matched anything real, always falling through to `input.value`. Fixed with real per-index reconstruction (`_flattened_messages()`).
- **`codegen/test_writer.py`'s `_normalize_llm_response` would have stringified a reconstructed message list wholesale** (`"[{'role': 'assistant', 'content': '...'}]"`) instead of extracting the actual reply text, the moment the otel importer fix above started producing that shape. Fixed to extract the last message's content, matching what a real `AIMessage.content` would hold.
- **`.env.example` documented a `GRAPHTRACE_JUDGE_API_KEY` variable that nothing in the codebase ever read.** `judge/client.py` never reads an env var itself -- `litellm.completion()` resolves the real provider key (`GROQ_API_KEY`, etc.) straight from the environment, based on the model string's own prefix. Fixed to document the real, working pattern (mirroring kbguard's own `.env.example`).
- A methodology bug caught mid-verification, not shipped: the first "clean venv" packaging check used `source venv/Scripts/activate`, which silently resolved `python`/`pip` to the *system* interpreter instead of the venv's own -- meaning it wasn't actually testing in isolation at all. Caught by checking `sys.executable`, not assumed correct; redone by invoking the venv's own `python.exe` directly.

### Changed (2026-10-26)
- `core/trajectory.py`'s `Step.index` now documented honestly: it reflects when LangGraph *started* a step's task, not necessarily the step's final position in `Trajectory.steps` -- a subgraph's `subgraph_exit` step is created (and indexed) when its wrapping task starts, but only committed after every one of its children, since a subgraph's own completion genuinely can't be known before they are. No `assert_*` function keys off `.index` today, so this was a safe, additive clarification, not a behavior change needing a migration.
- `importers/langsmith.py` and `importers/langfuse.py`'s field-name assumptions independently re-confirmed against real upstream sources (the LangSmith SDK's own `RunTree` test file + the official run-data-format doc; the current `GET /api/public/v2/observations` API reference) rather than left as original, unverified guesses -- both held up as correct. Where LangSmith actually stores an `llm` run's model name genuinely isn't documented anywhere; confirmed as a real gap in LangSmith's own docs, not just a gap in this project's research, and left honestly flagged rather than guessed at.

### Changed
- **Two corrections to the trace-to-test design, found only by actually trying to make a generated test replay-able against the real interceptor/engine layer, not by re-reading the architecture plan's description of it (2026-10-26):**
  1. **`replay/engine.py` gained a position-only fallback match for codegen's cassettes.** Every other cassette in this project matches a call by hashing its *exact* request — correct, because a real retry against the real graph reproduces the same request. An imported trace's own `request` field is whatever shape the *source observability platform* exported it in (Langfuse's JSON, an OTel attribute string, a LangSmith run's `inputs`), which structurally can never equal the real `str(list[BaseMessage])` the live LangGraph interceptor hashes at replay time — there is no transformation between the two that would make exact-hash matching work here. Fixed by having `codegen/test_writer.py` write cassette entries with a literal `any` hash segment (`node/kind/any/occurrence`), and teaching `resolve_call()` to try that position-only key only *after* the exact-hash lookup has already missed — so it can never shadow a real entry from a normal `record`-mode cassette.
  2. **The generated test's assertion narrowed from `assert_path` (exact sequence) to `assert_visited` (each node, at least once).** A trace importer only ever sees LLM/tool *calls* — a node that makes neither (a routing branch, a human-in-the-loop interrupt point) is invisible to every source platform's own export. Asserting the *exact* path from spans alone would therefore claim knowledge the trace never actually contained. Fixed before this ever generated a test that could silently fail on a perfectly correct run; `assert_path`/`assert_tool_calls_match` are suggested in the generated TODO for once the real path is known.
- **`codegen/test_writer.py`'s generated `graph = factory()` call now inspects the real target's signature first.** A LangGraph builder function commonly takes a chat model (or other required config) as an argument — this project's own `build_refund_graph(chat_model, ...)` is written exactly that way — so assuming every factory is zero-argument would silently generate a wrong call for a genuinely common, not edge-case, shape. `from-trace` now imports `--target` for real and checks for any required parameter, emitting a `# TODO: construct it the way your app really does` placeholder instead of guessing when one exists (or when the import itself fails).
- **Three corrections to the recording design, found only by running real code against real `langgraph`/`langchain-core` (1.2 / 1.6), not by re-reading the architecture plan's description of them:**
  1. **Call attribution moved off `contextvars` entirely.** The original design tracked "the current node" with a `ContextVar` set by the recorder and read back by the interceptors. Confirmed by hand with a `threading.current_thread()` probe inside a parallel ("fan-out") node: LangGraph's Pregel engine runs node functions — including parallel ones — on a `ThreadPoolExecutor` worker thread, and `ThreadPoolExecutor.submit()` doesn't propagate the calling thread's contextvars into the worker by default. A ContextVar set while consuming `graph.stream()` in the main thread reads back empty inside the node that's supposed to see it. Replaced with `config["metadata"]["langgraph_checkpoint_ns"]` — a `"{node_name}:{task_id}"` string LangGraph itself attaches to every LLM/tool call, confirmed by hand to be byte-for-byte the same `id` the debug event stream uses for that task, including across repeated visits to the same node in a retry loop. This correlation key travels with the call itself through whatever thread actually executes it — strictly more robust than the ContextVar design even if threading had cooperated.
  2. **Chat-model patch target moved from `_generate`/`_agenerate` to `invoke`/`ainvoke`.** Confirmed by hand (`'_generate' in GenericFakeChatModel.__dict__` is `True`) that every concrete chat model — OpenAI's, Anthropic's, and LangChain's own `GenericFakeChatModel` — defines its *own* `_generate`, overriding `BaseChatModel`'s. Patching the base class's `_generate` therefore patches a method real calls never resolve to; Python's method resolution finds the subclass's own override first, every time. `invoke`/`ainvoke` are never overridden by a concrete subclass (confirmed the same way) and carry the same `config["metadata"]` correlation key straight through — the same reasoning that already applied to tools (`BaseTool.invoke`, confirmed to be what LangGraph's real `ToolNode` actually calls, by reading its source, not `_run`).
  3. **`stream_mode` reduced from `["debug", "updates"]` to `["debug"]` alone.** Checked both side by side against a real run: `"updates"`'s per-node payload is exactly `task_result.result` already, under a different key. Subscribing to it bought nothing.
- `recorder.py` gained a `flush()` step and resume-deduplication beyond the original design: a step that pauses on an interrupt right after its `task_result` never gets a settling `checkpoint` event (confirmed by hand: the real debug-event stream for a paused run simply ends there) — `flush()` commits it anyway, using the graph's current `get_state(config).values`. Resuming re-runs that same node from the top under the **same task id** (confirmed by hand), so without dedup, the interrupted attempt's incomplete step would sit alongside the resumed, complete one as a duplicate; the recorder now replaces it instead.
- `plugin.py`'s scope reduced from the original plan: only the `run_graph` fixture is built. `--gt-mode` and the `cassette`/`judge` fixtures aren't added yet — they would do nothing today, and this project's own stated rule (`docs/project/contributing.md`) is not to ship a flag or fixture that doesn't actually do anything yet.

### Changed
- **Project renamed `graphcheck` → `graphtrace`** (2026-10-18). `graphcheck` is already published on PyPI as an unrelated Neo4j graph-data-quality tool — close enough in name and domain ("graph" + "check") to cause real confusion, and it would have blocked `pip install graphcheck` for this project entirely. Confirmed the collision via PyPI's simple index before renaming, and confirmed `graphtrace` was unclaimed on both PyPI and GitHub before committing to it. Renamed everything in one pass, not left half-done: the package (`src/graphtrace/`), every import, CLI flag names (`--gc-mode` → `--gt-mode`, etc.), the env var (`GRAPHCHECK_MODE` → `GRAPHTRACE_MODE`), the config filename (`graphcheck.yaml` → `graphtrace.yaml`), the internal plan doc, `LICENSE`/`NOTICE`/`README.md`, and the top-level folder itself (`D:\GraphCheck` → `D:\GraphTrace`).
- `Trajectory.cost_usd` changed from "sums tokens via a `runtime/pricing.py` lookup" (the original architecture plan's implied design) to "sums a `cost_usd` field already set per `LLMCall`." The original design would have made `core` import from `runtime`, which breaks this project's own layering rule (`core` must never depend on `runtime`) — the field-based approach keeps `core` genuinely pricing- and framework-ignorant. See [Core concepts: where cost comes from](../guide/trajectory-model.md#where-cost-comes-from).
- `assert_retries`' original architecture-plan example used a node name (`"tool_call"`) that didn't exist anywhere in the plan's own running example graph, and the function's semantics versus `assert_visits` were never actually specified. Fixed by giving it a concrete, narrower meaning — "re-entered after one of its own tool calls errored" — and a real example using an actual node name. See [Assertions: assert_retries](../guide/assertions.md#assert_retries).
- `assert_path`'s `...` gap matching scoped down from "however many gaps the syntax could technically support" to exactly one, with a second gap raising `ValueError` rather than silently picking an interpretation. See [Assertions: assert_path](../guide/assertions.md#assert_path).
- **Three features adopted from validated prior art, tagged and scoped (2026-10-21)** — a competitive-landscape review turned up real, evidenced tools worth copying rather than avoiding: `assert_tool_calls_match` (strict/unordered/subset/superset modes, straight from `langchain-ai/agentevals`, the official LangGraph ecosystem's own trajectory-match evaluator) **built and tested the same day** — 6 new tests, 37 total. Matches by tool *name* only, not args, a deliberate scope decision (agentevals treats sequence-matching and arg-matching as separate concerns; `assert_tool_called(..., args_match=...)` already covers the arg side). Cut-point replay (replay a recorded incident up to where it broke, then run a fix live from there, reusing the existing cassette-matching key unmodified — adopted from Chronicle, Microsoft, arXiv 2609.20625, whose own mutation-testing study is the evidence this is worth adopting) and statistical live-mode verification (a Wilson-interval Pass/Fail/Inconclusive verdict across N real trials instead of trusting one flaky nightly run — adopted from AgentAssay, arXiv 2603.02601) are both tagged **v0.2**, bundled with the already-planned security/observability work since all four build on the same shipped core. See [Cut-point replay](../guide/cut-point-replay.md), [Assertions: assert_tool_calls_match](../guide/assertions.md#assert_tool_calls_match), and [Recording & replay: statistical live-mode verification](../guide/recording-and-replay.md#statistical-live-mode-verification-v02).
- **CrewAI/AutoGen support planned and tagged v0.4** (2026-10-21). Previously an untagged, undesigned aspiration in the plan's non-goals list ("these can come later," no version, no design section) — now a real phase with a design (concept-mapping table, per-framework interceptor decision, one open question flagged rather than guessed) in the internal plan doc §20, and a file-by-file build plan. One architecture change made proactively in v0.1 itself as a result: the planned `runtime/` package was never built, so it's replaced before Week 1's recorder/runner land with `frameworks/base.py` (a `FrameworkRunner` Protocol) + `frameworks/langgraph/` (v0.1's only implementation) — meaning v0.4's `frameworks/crewai/`/`frameworks/autogen/` will be new packages, not a refactor of a shipped one. Config/CLI renamed ahead of need to match: `graph:` → `target:` (+ new `framework:` field), `--graph` → `--target`. See [Multi-framework support](../guide/multi-framework.md).
- The cassette format's `args`/`result` fields (tool-specific, per the original plan's sketch) became `request`/`response` — one consistent shape across both `kind: llm` and `kind: tool` entries turned out simpler than two different ones, and reads naturally either way ("the request", "the response").

### Fixed (caught before any of this shipped, not after)
- The architecture plan's component diagram was missing the `codegen`/test-writer node and the judge→cassette caching link that the plan's own prose (trace-to-test, judge contract) already described — fixed in the plan doc so the diagram and the text agree.
- The plan's cassette tech-stack choice listed "`PyYAML` / `ruamel.yaml`" as if interchangeable — plain `PyYAML`'s default dump doesn't actually guarantee the stable key order the plan's own goal ("cassettes diff well in PRs") depends on. Pinned to `ruamel.yaml` round-trip mode.
- The plan's trace-to-test section didn't say what happens to a human-in-the-loop interrupt on import — a resume value isn't recoverable from a trace. Fixed by specifying a `# TODO` stub instead of a guessed value, documented on [Trace-to-test](../guide/trace-to-test.md).
- **`ruamel.yaml`'s round-trip mode breaking a replayed value, found running real tests, not anticipated by any prior design pass**: a loaded float comes back as a `ScalarFloat` subclass (preserving its exact on-disk formatting, exactly what makes the cassette round-trip-identity guarantee true) — which then made LangGraph's own checkpointer raise `TypeError: Type is not msgpack serializable: ScalarFloat` the moment that value flowed into a replayed tool result and got persisted as graph state. Fixed with `replay/cassette.to_plain_python()`, applied only to a value about to flow back into real code, never to a value still destined for the cassette file — keeping both guarantees true at once instead of trading one for the other.
- An early draft of the replay error path re-raised *every* tool error (live or replayed) as a generic `RuntimeError`, which would have silently broken any node whose own `except SomeSpecificError:` depends on the real exception type — confirmed this would have broken Week 1's own `test_run_graph_tool_call_error_is_captured_without_crashing_when_node_catches_it` before it ever shipped. Fixed so only a *replayed* failure (genuinely unrecoverable type info once serialized to YAML) becomes a generic `RuntimeError`; a live exception always keeps its exact type via a bare `raise`.

### Design decisions locked in
- `core/` (data model + assertions) has zero dependencies on LangGraph, an LLM SDK, or `graphtrace.frameworks` — enforced by convention today (no lint rule yet; see [Contributing](contributing.md)).
- Framework-specific interception is **not** shared across frameworks, even though the `FrameworkRunner` Protocol and `Trajectory` output are. CrewAI and AutoGen don't reliably call through the same LangChain classes graphtrace's LangGraph interceptor patches, so each `frameworks/<name>/interceptors.py` targets that framework's own real call surface rather than assuming one patch covers all three.
- AutoGen's dynamic speaker selection vs. `assert_path`'s exact-match/single-gap model is an explicitly **open** question for v0.4, not assumed solved — see `graphtrace.md` §20.5. Documenting a gap honestly beats guessing an answer now and correcting it later.
- `TrajectoryAssertionError` subclasses `AssertionError`, not `Exception` — so a bare `assert` and an `assert_path(...)` failure look the same to pytest and to `pytest.raises(AssertionError)`.
- `assert_state_at`'s `occurrence` parameter follows Python list-indexing (`-1` = most recent visit, `0` = first) rather than inventing a new convention.
- `any_str()` is the only matcher built — more are added when a real test needs one, not speculatively.
- Licensing: Apache-2.0, single license, no feature gating, plus a lightweight CLA policy — decided before any commercial scope existed, so it never has to be partially undone later. See the project's internal plan doc, section 17.
- `replay/engine.py`'s `resolve_call()` never imports LangChain or LangGraph, and never sees an `AIMessage`/`ToolMessage` object — only plain dicts/strings/numbers. All LangChain-specific serialization lives in `frameworks/langgraph/interceptors.py`, on either side of the call into `resolve_call()`. This is the actual test of whether record/replay stays reusable for v0.4's CrewAI/AutoGen interceptors, not just an aspiration.
- Redaction (`graphtrace.yaml`'s `replay.redact`) is validated but deliberately not enforced yet — shipping a config field that *looks* like it protects secrets before it actually does would be worse than not having the field at all. Documented as an open gap everywhere it's relevant (`docs/guide/recording-and-replay.md`, `docs/guide/configuration.md`), not silently assumed.
